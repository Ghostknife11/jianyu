# Public synthetic model benchmark v0.1

This is the beginning of the manually operated v0.1 model-compatibility process, not a model recommendation. All six cases in [`v0.1-cases.json`](v0.1-cases.json) are fictional. Never insert a family's real context, child's name, history, school results, or API key into this corpus or a committed response file.

The cases exercise the distinctive FOE task: 4–6 co-play without developmental scoring; one interest opening genuinely different doors; a teenager's refusal; no time/energy; unverified local events; and conflicting observations. The two 10–12 cases also require human review of wording that child and caregiver can read together without converting a caregiver goal into the child's wish. The client will always add `Nothing` itself, so a model that has no natural entry returns `{"opportunities":[]}`. It must not fabricate a `Nothing` candidate merely to fill the list.

Each `context` object is the exact JSON projection produced by the current Android Context Firewall and `buildOpportunityTaskPrompt`, not a separate benchmark-only input format. Its `regionAsEntered` name does **not** guarantee that user-entered text is coarse. The optional seven-day selected-option count is absent in these cases because the client does not disclose it without per-call opt-in. [`PublicBenchmarkPromptParityTest.kt`](../../apps/jianyu-android/core/data/src/test/kotlin/org/jianyu/core/data/PublicBenchmarkPromptParityTest.kt) checks every case against the production builder. [`PublicBenchmarkPipelineTest.kt`](../../apps/jianyu-android/core/data/src/test/kotlin/org/jianyu/core/data/PublicBenchmarkPipelineTest.kt) additionally replays the hand-written synthetic example through the actual Android parser, Gate, selector, and Nothing path; it also checks a zero-minute adversarial candidate. Neither test calls or grades a real model. When changing the prompt, firewall, parser, or Policy, update the fictional cases deliberately and keep both tests passing.

## How an operator runs it

1. Pin the repository commit, Android prompt/response contract, Provider endpoint, exact model ID, temperature, and run date. Use the `OPPORTUNITY_SYSTEM_PROMPT` and `buildOpportunityTaskPrompt` contract in [`OpenAiCompatibleOpportunitySource.kt`](../../apps/jianyu-android/core/data/src/main/kotlin/org/jianyu/core/data/OpenAiCompatibleOpportunitySource.kt). Replace only the `<family-context-json>` value with one fictional case's `context` JSON at a time; keep every other prompt sentence, the system prompt, and the response contract unchanged. Run the Android parity test before an assessment. A future runner should invoke the same builder directly; do not maintain a second drifting production prompt here.
2. Obtain explicit permission for the test call from the account/key owner. A model service may bill or retain these fictional requests. Never run the suite automatically when a family opens the App.
3. Run every case at least three times when making a publishable comparison. Keep raw synthetic responses and request timing in a private test workspace, not in the family vault or this repository. The evaluator accepts a JSON file shaped as `{ "model": "exact-model-id", "responses": { "co-play-water": { "opportunities": [...] }, "...": { "opportunities": [] } } }`. Each response may also be a JSON string containing the model's raw structured output.
4. Screen one run with `node scripts/evaluate-model-benchmark.mjs models/benchmark/v0.1-cases.json <responses.json>`. To check the runner itself, substitute [`example-run.synthetic.json`](example-run.synthetic.json); it is hand-written test data, not a real model result. The report contains only case IDs, counts, ecosystems, machine findings, and questions for human review; it does not echo candidate text or keys. Exit code 1 means at least one machine finding. An empty array is expected in the refusal and no-capacity cases, but repeatedly returning empty arrays for positive cases is a failure too. This separate JavaScript screen does **not** run a recorded real response through the Android Gate; its synthetic replay test is a regression for the example fixture only.
5. A human reviews every response for naturalness, concrete feasibility, real multi-ecosystem diversity, child agency, avoidance of disguised lessons and fixed child labels, source claims, freshness, and “surprising but useful” value. Compare against a plain chat baseline on the same synthetic cases. The machine screen shares the JavaScript reference Gate's narrow clause check across title, explanation, and why-now text for an explicit daily assignment, regardless of a model's child-pull or pressure claim. It can miss differently worded pressure and flag a genuinely voluntary daily practice phrased as an assignment. It cannot decide recommendation quality, validate a real event, or stand in for the full Android Opportunity Gate.
6. Only then may maintainers publish a versioned compatibility entry with the sample count, model/provider IDs, dates, prompt hash, latency and cost observations, machine findings, human-review method, failures, and limitations. No real model is currently rated. The existing `models/compatibility.demo.json` contains fictional demonstration entries only.

Do not turn these cases into a fixed set of five required activities. The right answer can have one door or no door. The suite deliberately combines mechanical failures with judgment-heavy checks, and a clean machine report is never a safety certificate, education outcome claim, or model recommendation.
